# 0001. 관계형 데이터베이스로 PostgreSQL 선택

## 상태
Accepted

## 배경
가계부 서비스의 핵심 데이터(지출 내역, 카테고리, 통계 등)를 저장할 RDBMS가 필요했다.
지출 데이터는 금액, 일시, 카테고리 등 정형화된 구조를 가지며, 집계/통계 쿼리가 빈번하게 발생할 것으로 예상된다.

## 결정
PostgreSQL 선택.

## 근거
- **ACID 트랜잭션**: 금액 데이터 정합성이 중요한 가계부 특성상 필수
- **집계 함수 / 윈도우 함수**: 월별 지출 합계, 카테고리별 통계 등 복잡한 분석 쿼리에 강점
- **JSONB 타입**: 향후 AI 분석 결과나 카드사 SMS 파싱 데이터처럼 비정형 데이터를 별도 테이블 없이 저장 가능
- **오픈소스 & 무료**: 라이선스 비용 없이 프로덕션 사용 가능
- **실무 표준**: AWS RDS, GCP Cloud SQL 등 클라우드 환경에서 PostgreSQL이 사실상 기본 선택지

## 대안

| 대안 | 탈락 이유 |
|------|----------|
| MySQL | GROUP BY 처리 방식이 표준 SQL과 달라 복잡한 집계 쿼리에서 혼란을 유발. PostgreSQL 대비 윈도우 함수 지원이 약함 |
| H2 (인메모리) | 개발/테스트 편의성은 높지만, prod 환경과 DB 동작 차이가 숨은 버그를 만들 수 있어 처음부터 PostgreSQL로 통일 |
| SQLite | 단일 파일 DB로 동시성 처리 한계, 서버 환경 부적합 |

## 결과
- **긍정적**: 실무와 동일한 환경에서 개발 가능, 집계 API 구현 시 DB 기능을 최대한 활용 가능
- **부정적**: 로컬 개발 환경에 PostgreSQL 설치 또는 Docker 실행이 필요 (H2 대비 초기 셋업 비용 존재)
